# 실행·종료·상태 복구

## 실행 방식

| 명령 | 실행 범위 |
|---|---|
| `npm start` | Discord만 |
| `npm run start:slack` | Slack만 |
| `./scripts/start.command` | Aside 앱·CLI 연결 확인 후 두 봇 함께 |
| `npm run service:install` | 현재는 Discord만 LaunchAgent로 설치 |

각 시작 명령은 소스를 빌드합니다. 함께 실행할 때 실행기 하나가 두 자식 프로세스를 관리합니다. Control+C나 한 봇 종료 시 함께 시작한 다른 봇도 정상 종료합니다. 이미 별도로 실행 중인 다른 봇을 종료하지 않습니다.

LaunchAgent 설치는 사용자 `Library/LaunchAgents`에 파일을 쓰고 등록하는 운영 변경입니다. Keychain·Aside 연결을 먼저 확인하며 기존 설치를 덮어쓰지 않습니다. 로그아웃 중의 서버나 Slack 서비스 설치는 제공하지 않습니다. 전경 실행과 서비스 설치를 동시에 하지 마세요. 정상 종료 코드 0은 자동 재시작하지 않습니다.

Slack의 채널 스레드 자동 응답은 `channelThreadAutoReply: false`가 기본입니다. `config.slack.local.json` 또는 우선 적용되는 환경변수 `ASIDE_SLACK_THREAD_AUTO_REPLY=true|false`를 변경한 뒤 정상 재시작합니다. 시작 기록의 실제 적용값·PID와 프로세스 생존을 함께 확인하세요. 이 옵션을 꺼도 명시 멘션·첫 호출 맥락 읽기·DM·Discord는 유지하며 Slack 이벤트 구독이나 Keychain은 변경하지 않습니다. [설정 예시](slack-setup.md#스레드-자동-응답-기본-꺼짐)를 참고하세요.

## 잠금·준비 상태·로그

Discord 데이터는 `dataDir`, Slack 데이터는 `dataDir/slack`에 있습니다. 각 플랫폼은 DB·레지스트리·잠금을 따로 사용합니다.

- `service.lock`: 실행 PID. 살아 있거나 확인할 수 없는 PID는 중복 실행을 차단합니다.
- `service.lock.guard`: macOS 커널 잠금용 파일. 임의 삭제하지 않습니다.
- `startup-status.json`: 준비 완료 PID·시간. 잠금 PID·실제 프로세스와 일치할 때만 해당 실행의 근거입니다. 계속 연결되어 있다는 실시간 보장은 아닙니다.
- `state.sqlite`·WAL·SHM: 대화 매핑·요청·전송 대기열.
- `aside-registry.json`·`aside-registry.key`: 세션 소유권 검증 자료. 둘 다 비공개로 보존해야 기존 세션을 검증할 수 있습니다.
- Discord LaunchAgent 로그: `service.log`, `service-error.log`. 전경 실행은 해당 터미널에 표시합니다.

죽은 PID 잠금은 다음 시작 시 원본을 recovery 폴더에 보관하고 복구합니다. 불명확한 잠금은 지우지 않습니다. 질문·토큰·원시 CLI 출력은 정상 로그에 기록하지 않습니다. 로그·진단·복구 파일은 게시 목록에서 제외합니다.

## 잠자기와 업데이트

`/usr/bin/caffeinate -i -w <봇 PID>`로 자동 유휴 시스템 잠자기를 막습니다. 화면은 꺼질 수 있고 덮개 닫기·수동 잠자기·로그아웃·전원 종료까지 방지하지는 않습니다. 종료 시 해제하며 macOS 전원 설정을 바꾸지 않습니다.

편집·빌드만으로 이미 실행 중인 프로세스에 변경이 적용되지는 않습니다. 업데이트 후에는 대기·실행·불명확 요청과 미전송 답변을 확인하고 작업이 없는 때 정상 종료·시작하세요. 커맨드를 추가로 실행해 중복 서버를 만들지 마세요. Discord `/aside shutdown confirm:true`는 소유자·채널·확인을 검사합니다. Slack에는 서버 종료 명령이 없습니다.

## 상태가 불명확할 때

실행 불명확과 전송 불명확은 다릅니다. 실행 불명확 요청 하나가 해당 플랫폼 전체의 새 질문을 차단합니다. 반대 플랫폼은 별도 대기열을 사용합니다.

1. Discord `/aside status` 또는 Slack `!aside status`로 상태를 확인합니다.
2. 로컬 DB 매핑으로 연결된 Aside 세션을 확인합니다. 같은 질문 중복 실행이나 DB 삭제로 해결하지 않습니다.
3. 중단을 원하면 원래 스레드에서 stop 명령을 사용합니다. `interrupted`는 요청 수락이며 완전 종료 확인과 다릅니다. 불명확한 stop은 같은 스레드에서 재확인할 수 있습니다.
4. 재확인 대상은 `stop_unconfirmed`·`stop_failed`입니다. 서버 재시작의 `interrupted`, 실행·세션 생성 시간 초과는 자동 해제하지 않습니다. 소유권·턴 종료·결과를 운영자가 확인해야 합니다. 보편적인 강제 해제 명령은 없습니다.
5. DB 변경이 필요하면 먼저 비공개 백업을 만들고 정확한 요청만 복구합니다. 완료 사실과 전송 여부를 구분합니다. 답변을 전송 대기열에 등록하면 자동 전송과 같은 요청의 안내 정리가 발생할 수 있습니다.

연결된 Aside 세션이 없어 완료 여부를 확인할 수 없는 과거 실행 불명확 요청은 성공으로 바꾸지 않습니다. 정상 SDK 조회로 세션 부재를 확인하고 다른 활성 작업·전송 대기가 없는지 검사합니다. 운영자가 결과 미확인 중단을 명시 승인한 경우에만 DB를 비공개 백업한 뒤 그 요청을 `cancelled / operator_abandoned_result_unknown`으로 종결하고, 해당 스레드의 다른 불명확 요청이 없을 때 차단을 해제합니다. 대화·전송 기록과 기존 세션 매핑은 보존하며 질문이나 답변을 자동 재실행·재전송하지 않습니다. 세션 부재만으로 과거 작업의 완료 또는 결과를 추정하지 않습니다.

새 질문을 제출하기 전 정상 SDK가 정확한 세션 ID에 대해 `Session not found`를 반환하면 그 질문은 실행 전 실패로 처리하고 새 대화를 안내합니다. 없는 세션을 자동으로 대체하거나 같은 질문을 다시 보내지 않으며 다른 대화의 새 실행을 차단하지 않습니다. 연결·인증·메시지 검증 오류나 제출 후의 불명확 상태는 계속 기존 보수적인 차단 규칙을 따릅니다. Slack은 새 최상위 `@Aside 질문` 또는 새 DM 질문으로, Discord는 새 스레드 생성 명령으로 새 대화를 시작합니다.

Discord는 nonce 중복 방지의 유효 시간 안에서만 답변 전송을 재시도합니다. Slack은 응답 수신 여부가 불명확한 POST를 자동 재시도하지 않습니다. 원 질문을 자동 재실행하는 것은 아닙니다.

## 진단 범위

`npm run doctor`는 CLI 연결을 확인하고 비공개 진단 파일을 저장합니다. 설정·토큰을 고치거나 실제 모델 답변을 생성하지 않습니다. `npm run certify`는 과거 검색 전용 정책 검증용이며 새 probe 세션을 만듭니다. 일반 시작·문서 검사의 필수 명령이 아닙니다.

현재 PID·잠금·준비 기록·플랫폼 연결을 함께 확인하세요. 로컬 모의 테스트 통과와 실제 질문→모델 완료→원래 스레드 답변 검증을 별도로 기록합니다.

## 메뉴 바 관리자 운영

2026-10-02 읽기 전용 점검에서 메뉴바 앱이 두 봇을 자식 프로세스로 관리하며 가동 중임을 확인했습니다. 두 봇 모두 `connected`, 초기 검증 통과·엔진 준비 완료·절전 방지 활성화였고 보고된 오류는 없었습니다. 이는 확인 시점의 상태이며 질문·답변 왕복, 대기열의 비어 있음, 장애 복구 성공을 보장하지 않습니다. 최신 현황과 검증 한계는 [프로젝트 개요서](../프로젝트%20개요서.md)를 참고하세요.

메뉴의 개별 상태와 관리 상태를 함께 확인하세요. 정상 아이콘은 두 봇 모두 SDK 연결과 초기 안전 검증·엔진 준비가 확인된 경우에만 나타납니다. 재연결은 프로세스 종료와 다르며, 실시간 제어 응답이 오래되거나 절전에서 복귀하면 상태가 확인 불가로 바뀝니다. 원문 SDK·CLI 출력 대신 고정된 오류 설명과 플랫폼별 안전 이벤트 로그를 표시합니다. 로그는 `~/Library/Application Support/AsideBotMenu/Logs` 아래 0600 파일, 플랫폼별 1 MiB와 이전 파일 1개로 제한합니다. 관찰 중인 외부 실행의 터미널 원문은 수집하지 않습니다.

관리 연결이 끊기면 해당 봇은 정상 종료합니다. 관리 중인 한쪽 프로세스가 예기치 않게 종료하면 다른 쪽에도 정상 종료를 요청합니다. 종료 명령 수락이나 소켓 해제만으로 프로세스 종료를 확정하지 않습니다. 앱 종료가 30초 넘게 걸리면 OS의 현재 종료 요청을 취소하고 기다리기 또는 앱 종료 취소를 안내합니다. 봇 정리는 계속되며 취소가 봇 재시작을 뜻하지 않습니다. 강제 종료로 완료를 가장하지 않습니다.

SDK 연결 초기화 도중 종료를 요청하면 진행 중인 초기화가 정착한 뒤 SDK를 해제합니다. 네트워크 지연으로 종료가 길어질 수 있으며, 이 동안 잠금과 관리 연결을 유지하고 종료 완료로 표시하지 않습니다.

운영 전환 전에 실제 실행 상태·대기열·실행 불명확 요청·미전송 답변과 LaunchAgent를 읽기 전용으로 확인하세요. 앱 배치·기존 실행 인계·로그인 등록은 사용자의 별도 운영 지시 후 수행합니다. 네트워크 차단이나 진행 중인 요청 중단도 영향을 알리고 별도 지시에 따릅니다. 잠금·DB·레지스트리를 수동 삭제하지 않습니다.

CLI 방식으로 돌아가려면 관리 봇의 실제 종료를 확인한 후 앱을 닫고 기존 `scripts/start.command`를 실행합니다. 로그인 항목 해제는 앱의 사용자 토글로 처리합니다. 외부 실행은 앱 종료로 중지하지 않습니다.

인계 조사 도중 정상 중지를 요청하면 진행 중인 조사도 취소 대상으로 유지하며, 조사 완료 후 외부 봇에 종료 신호를 보내거나 다시 시작하지 않습니다. 메뉴를 열어 둔 상태에서도 상태 갱신 타이머는 계속 동작합니다. 두 경로는 모의 프로세스·메뉴 추적 run-loop 회귀 테스트로 검증하며, 실제 서비스 인계와 GUI 수용 검증을 대신하지 않습니다.
