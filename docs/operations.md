# 실행·종료·상태 복구

## 실행 방식

| 명령 | 실행 범위 |
|---|---|
| `npm start` | Discord만 |
| `npm run start:slack` | Slack만 |
| `./scripts/start.command` | Aside 앱·CLI 연결 확인 후 두 봇 함께 |
| `npm run service:install` | 현재는 Discord만 LaunchAgent로 설치 |

각 시작 명령은 소스를 빌드합니다. 함께 실행할 때 실행기 하나가 두 자식 프로세스를 관리합니다. Control+C나 한 봇 종료 시 함께 시작한 다른 봇도 정상 종료합니다. 이미 별도로 실행 중인 다른 봇을 종료하지 않습니다.

LaunchAgent 설치는 사용자 `Library/LaunchAgents`에 파일을 쓰고 등록하는 운영 변경입니다. Keychain·Aside 연결을 먼저 확인하며 기존 설치를 덮어쓰지 않습니다. 로그아웃 중의 서버나 Slack 서비스 설치는 제공하지 않습니다. 전경 실행과 서비스 설치를 동시에 하지 마세요. 정상 종료 코드 0은 자동 재시작하지 않습니다.

Slack의 채널 스레드 자동 응답은 `channelThreadAutoReply: false`가 기본입니다. `config.slack.local.json` 또는 우선 적용되는 환경변수 `ASIDE_SLACK_THREAD_AUTO_REPLY=true|false`를 변경한 뒤 정상 재시작합니다. 시작 기록의 실제 적용값·PID와 프로세스 생존을 함께 확인하세요. 이 옵션을 꺼도 명시 멘션·첫 호출 맥락 읽기·DM·Discord는 유지하며 Slack 이벤트 구독이나 Keychain은 변경하지 않습니다. [설정 예시](slack-setup.md#스레드-자동-응답-기본-꺼짐)를 참고하세요.

## 잠금·준비 상태·로그

Discord 데이터는 `dataDir`, Slack 데이터는 `dataDir/slack`에 있습니다. 각 플랫폼은 DB·레지스트리·잠금을 따로 사용합니다.

- `service.lock`: 실행 PID. 살아 있거나 확인할 수 없는 PID는 중복 실행을 차단합니다.
- `service.lock.guard`: macOS 커널 잠금용 파일. 임의 삭제하지 않습니다.
- `startup-status.json`: 준비 완료 PID·시간. 잠금 PID·실제 프로세스와 일치할 때만 해당 실행의 근거입니다. 계속 연결되어 있다는 실시간 보장은 아닙니다.
- `state.sqlite`·WAL·SHM: 대화 매핑·요청·전송 대기열.
- `aside-registry.json`·`aside-registry.key`: 세션 소유권 검증 자료. 둘 다 비공개로 보존해야 기존 세션을 검증할 수 있습니다.
- Discord LaunchAgent 로그: `service.log`, `service-error.log`. 전경 실행은 해당 터미널에 표시합니다.

죽은 PID 잠금은 다음 시작 시 원본을 recovery 폴더에 보관하고 복구합니다. 불명확한 잠금은 지우지 않습니다. 질문·토큰·원시 CLI 출력은 정상 로그에 기록하지 않습니다. 로그·진단·복구 파일은 게시 목록에서 제외합니다.

## 잠자기와 업데이트

`/usr/bin/caffeinate -i -w <봇 PID>`로 자동 유휴 시스템 잠자기를 막습니다. 화면은 꺼질 수 있고 덮개 닫기·수동 잠자기·로그아웃·전원 종료까지 방지하지는 않습니다. 종료 시 해제하며 macOS 전원 설정을 바꾸지 않습니다.

편집·빌드만으로 이미 실행 중인 프로세스에 변경이 적용되지는 않습니다. 업데이트 후에는 대기·실행·불명확 요청과 미전송 답변을 확인하고 작업이 없는 때 정상 종료·시작하세요. 커맨드를 추가로 실행해 중복 서버를 만들지 마세요. Discord `/aside shutdown confirm:true`는 소유자·채널·확인을 검사합니다. Slack에는 서버 종료 명령이 없습니다.

완료가 검증된 답변의 웹 검색 출처는 개별 검증합니다. 잘못된 형식·파싱 불가능한 주소·HTTP(S) 이외의 주소·사용자 정보가 포함된 주소는 제외하고 답변 본문과 유효한 출처는 전달합니다. 출처 목록 자체가 잘못된 형식이면 그 목록만 제외합니다. 완료·모델·소유권 검증은 유지하며, 과거 `completed_output_invalid_sources` 실패 요청을 패치나 재시작으로 자동 재실행·재전송하지 않습니다.

## 상태가 불명확할 때

실행 불명확과 전송 불명확은 다릅니다. 실행 불명확 요청 하나가 해당 플랫폼 전체의 새 질문을 차단합니다. 반대 플랫폼은 별도 대기열을 사용합니다.

1. Discord `/aside status` 또는 Slack `!aside status`로 상태를 확인합니다.
2. 로컬 DB 매핑으로 연결된 Aside 세션을 확인합니다. 같은 질문 중복 실행이나 DB 삭제로 해결하지 않습니다.
3. 중단을 원하면 원래 스레드에서 stop 명령을 사용합니다. `interrupted`는 요청 수락이며 완전 종료 확인과 다릅니다. 불명확한 stop은 같은 스레드에서 재확인할 수 있습니다.
4. 재확인 대상은 `stop_unconfirmed`·`stop_failed`입니다. 서버 재시작의 `interrupted`, 실행·세션 생성 시간 초과는 자동 해제하지 않습니다. 소유권·턴 종료·결과를 운영자가 확인해야 합니다. 보편적인 강제 해제 명령은 없습니다.
5. DB 변경이 필요하면 먼저 비공개 백업을 만들고 정확한 요청만 복구합니다. 완료 사실과 전송 여부를 구분합니다. 답변을 전송 대기열에 등록하면 자동 전송과 같은 요청의 안내 정리가 발생할 수 있습니다.

연결된 Aside 세션이 없어 완료 여부를 확인할 수 없는 과거 실행 불명확 요청은 성공으로 바꾸지 않습니다. 정상 SDK 조회로 세션 부재를 확인하고 다른 활성 작업·전송 대기가 없는지 검사합니다. 운영자가 결과 미확인 중단을 명시 승인한 경우에만 DB를 비공개 백업한 뒤 그 요청을 `cancelled / operator_abandoned_result_unknown`으로 종결하고, 해당 스레드의 다른 불명확 요청이 없을 때 차단을 해제합니다. 대화·전송 기록과 기존 세션 매핑은 보존하며 질문이나 답변을 자동 재실행·재전송하지 않습니다. 세션 부재만으로 과거 작업의 완료 또는 결과를 추정하지 않습니다.

새 질문을 제출하기 전 정상 SDK가 정확한 세션 ID에 대해 `Session not found`를 반환하면 그 질문은 실행 전 실패로 처리하고 새 대화를 안내합니다. 없는 세션을 자동으로 대체하거나 같은 질문을 다시 보내지 않으며 다른 대화의 새 실행을 차단하지 않습니다. 소유권·메시지·모델 검증 오류나 제출 후의 불명확 상태는 계속 기존 보수적인 차단 규칙을 따릅니다. Slack은 새 최상위 `@Aside 질문` 또는 새 DM 질문으로, Discord는 새 스레드 생성 명령으로 새 대화를 시작합니다.

세션 생성 CLI 응답이 끊기면 동일한 bootstrap 고유 표식·사용자 입력·선택 모델의 완료 답변을 읽기 전용으로 확인합니다. 정확히 하나만 확인되면 레지스트리에 등록하고 정상 진행합니다. 생성 명령이 정상 종료했지만 전체 세션 목록이 비었거나 새 세션 모두에 대해 정확한 `Session not found`가 확인되면 `failed / session_creation_unavailable`로 처리합니다. 사용자 질문은 제출하지 않았고 다른 질문의 실행을 차단하지 않습니다. CLI 실패·시간 초과 후의 세션 부재만으로는 자동 해제하지 않습니다.

세션 ID가 없는 `uncertain / session_creation_unknown` 요청의 결과 미확인 중단에는 제한된 운영 명령을 사용할 수 있습니다.

```sh
npm run recover:creation -- slack 19
# 실제 적용 전 메뉴바 앱을 정상 종료합니다. 요청 번호는 조회 결과로 확인하세요.
npm run recover:creation -- slack 19 --abandon-unsubmitted
```

첫 명령은 조회만 합니다. 두 번째 명령의 플래그는 해당 요청의 결과를 미확인 상태로 종결한다는 운영자 확인입니다. 서비스 잠금 획득, 대기·실행 요청과 미전송 기록 부재, 정상 CLI 버전과 전체 세션 목록을 확인합니다. 모든 남은 세션의 변경 시각이 요청 생성보다 최소 1분 이전이고 실행 중 상태가 없어야 합니다. 근거가 부족하거나 연결된 세션·다른 오류 코드가 있으면 거부합니다. 적용 직전 비공개 SQLite 백업을 생성하고 해당 요청만 `cancelled / operator_abandoned_result_unknown`으로 변경합니다. 다른 불명확 요청의 차단은 유지하며 질문·답변을 자동 실행하거나 전송하지 않습니다. 적용 후 메뉴바 앱을 다시 시작하세요. Discord는 첫 인자를 `discord`로 지정합니다.

Discord는 nonce 중복 방지의 유효 시간 안에서만 답변 전송을 재시도합니다. Slack은 응답 수신 여부가 불명확한 POST를 자동 재시도하지 않습니다. 원 질문을 자동 재실행하는 것은 아닙니다.

## 인터넷 단절·절전 복귀

Discord는 SDK의 Gateway 재연결을 사용합니다. Slack은 Socket Mode 연결을 별도 루프로 관리하며 연결 실패 후 5초부터 최대 60초 간격으로 계속 재시도합니다. HTTP 429의 `Retry-After`는 따르고, 토큰 무효·권한 부족 등 확인된 인증 오류는 무한 재시도하지 않습니다. 초기 연결 중에도 정상 종료로 재시도를 취소할 수 있습니다. 30초를 넘는 절전 공백이 있으면 Slack의 오래된 소켓을 닫고 다시 연결합니다.

플랫폼 연결이 끊긴 동안 아직 제출하지 않은 질문과 미시도 답변은 대기합니다. 질문 준비·세션 생성·실행 전 확인 도중 끊겨도 사용자 질문이 제출되지 않은 것이 확인되면 원문을 보존해 대기열로 돌립니다. 연결 복구 후 처리하지만 기존 대기열의 15분 만료는 유지합니다. 장시간 단절로 만료된 질문은 자동 실행하지 않고 만료 안내를 전송합니다. 봇이 받지 못한 플랫폼 메시지의 재전달은 플랫폼에 달려 있습니다.

세션 생성 명령 또는 질문 제출 전에 발생한 CLI 통신 오류는 `session_preflight_unavailable`로 안전 실패 처리합니다. 플랫폼도 끊긴 상태라면 대기하며, 플랫폼 연결이 살아 있으면 미제출 안내를 보내 사용자가 다시 시도하도록 합니다. 이 오류만으로 대화를 불명확 상태로 차단하지 않습니다. 생성 명령을 이미 시작했거나 소유권·메시지 검증이 실패한 경우에는 이 규칙을 적용하지 않습니다.

이미 질문을 제출했으면 접수 응답이 유실되어도 같은 질문을 다시 보내지 않습니다. CLI 통신 오류 뒤에는 같은 세션의 완료 기록 조회만 1초부터 최대 30초 간격으로 재시도합니다. 기존 60분 완료 확인 한도를 넘으면 불명확 상태를 유지합니다. 완료 답변은 로컬 전송 대기열에 저장하고 플랫폼 연결이 돌아온 뒤 전송합니다. Slack POST를 이미 시도해 결과가 불명확해진 경우에는 자동 재전송하지 않습니다.

Mac이 실제 잠든 동안에는 봇도 실행되지 않습니다. 덮개 닫기·수동 잠자기 중 응답까지 보장하려면 계속 켜져 있는 호스트가 필요합니다. 이 패치는 복귀 후 연결과 대기 작업의 복구를 다룹니다. Aside에서 사라진 기존 세션의 대화 내용이나 지속성을 복구하는 기능은 제공하지 않습니다.

## 진단 범위

`npm run doctor`는 CLI 연결을 확인하고 비공개 진단 파일을 저장합니다. 설정·토큰을 고치거나 실제 모델 답변을 생성하지 않습니다. `npm run certify`는 과거 검색 전용 정책 검증용이며 새 probe 세션을 만듭니다. 일반 시작·문서 검사의 필수 명령이 아닙니다.

현재 PID·잠금·준비 기록·플랫폼 연결을 함께 확인하세요. 로컬 모의 테스트 통과와 실제 질문→모델 완료→원래 스레드 답변 검증을 별도로 기록합니다.

## 메뉴 바 관리자 운영

2026-10-14부터 메뉴바 앱은 Slack만 시작·중지·인계합니다. 메뉴의 `Slack 시작`, `Slack 정상 중지`, `앱 실행 시 Slack 자동 시작`을 사용하세요. `로그인 시 앱 실행`과 `앱 실행 시 Slack 자동 시작`을 모두 켜면 Mac 로그인 후 Slack만 자동 실행하며 Discord는 앱에서 비활성화 상태로 유지합니다. Slack 단독 연결은 정상 아이콘으로 표시하며 Discord 실행 파일이나 잠금은 Slack 시작을 막지 않습니다. 기존 CLI의 Discord 실행·두 봇 실행 명령은 별도 수동 운영용으로 남아 있습니다.

2026-10-02 읽기 전용 점검에서 메뉴바 앱이 두 봇을 자식 프로세스로 관리하며 가동 중임을 확인했습니다. 두 봇 모두 `connected`, 초기 검증 통과·엔진 준비 완료·절전 방지 활성화였고 보고된 오류는 없었습니다. 이는 확인 시점의 상태이며 질문·답변 왕복, 대기열의 비어 있음, 장애 복구 성공을 보장하지 않습니다. 최신 현황과 검증 한계는 [프로젝트 개요서](../프로젝트%20개요서.md)를 참고하세요.

메뉴의 Slack 상태와 관리 상태를 함께 확인하세요. 정상 아이콘은 Slack의 SDK 연결과 초기 안전 검증·엔진 준비가 확인된 경우에만 나타납니다. 재연결은 프로세스 종료와 다르며, 실시간 제어 응답이 오래되거나 절전에서 복귀하면 상태가 확인 불가로 바뀝니다. 원문 SDK·CLI 출력 대신 고정된 오류 설명과 플랫폼별 안전 이벤트 로그를 표시합니다. 로그는 `~/Library/Application Support/AsideBotMenu/Logs` 아래 0600 파일, 플랫폼별 1 MiB와 이전 파일 1개로 제한합니다. 관찰 중인 외부 실행의 터미널 원문은 수집하지 않습니다.

준비를 마친 앱 관리 봇이 오류로 종료되면 메뉴바 앱이 다음 상태 갱신에서 한 번 다시 시작합니다. 시작 중 실패나 사용자가 요청한 중지에는 자동 복구가 적용되지 않습니다.

관리 연결이 끊기면 Slack은 정상 종료합니다. 종료 명령 수락이나 소켓 해제만으로 프로세스 종료를 확정하지 않습니다. 앱 종료가 30초 넘게 걸리면 OS의 현재 종료 요청을 취소하고 기다리기 또는 앱 종료 취소를 안내합니다. 봇 정리는 계속되며 취소가 봇 재시작을 뜻하지 않습니다. 강제 종료로 완료를 가장하지 않습니다.

SDK 연결 초기화 도중 종료를 요청하면 진행 중인 초기화가 정착한 뒤 SDK를 해제합니다. 네트워크 지연으로 종료가 길어질 수 있으며, 이 동안 잠금과 관리 연결을 유지하고 종료 완료로 표시하지 않습니다.

운영 전환 전에 실제 실행 상태·대기열·실행 불명확 요청·미전송 답변과 LaunchAgent를 읽기 전용으로 확인하세요. 앱 배치·기존 실행 인계·로그인 등록은 사용자의 별도 운영 지시 후 수행합니다. 네트워크 차단이나 진행 중인 요청 중단도 영향을 알리고 별도 지시에 따릅니다. 잠금·DB·레지스트리를 수동 삭제하지 않습니다.

CLI 방식으로 돌아가려면 관리 봇의 실제 종료를 확인한 후 앱을 닫고 기존 `scripts/start.command`를 실행합니다. 로그인 항목 해제는 앱의 사용자 토글로 처리합니다. 외부 실행은 앱 종료로 중지하지 않습니다.

인계 조사 도중 정상 중지를 요청하면 진행 중인 조사도 취소 대상으로 유지하며, 조사 완료 후 외부 봇에 종료 신호를 보내거나 다시 시작하지 않습니다. 메뉴를 열어 둔 상태에서도 상태 갱신 타이머는 계속 동작합니다. 두 경로는 모의 프로세스·메뉴 추적 run-loop 회귀 테스트로 검증하며, 실제 서비스 인계와 GUI 수용 검증을 대신하지 않습니다.

## 전송 실패 진단

Slack 전송 전 검증·정상 종료에 따른 미시도 및 확인된 API 거절은 `전송 실패`로, POST 시간 초과·응답 유실·확인 불가능한 오류는 `전송 불명확`으로 구분합니다. 두 경우 모두 자동 재전송하지 않으며 같은 답변의 남은 조각도 보류합니다. 실제 발송 여부를 확인한 뒤 별도 운영 절차로 처리하세요.

저장소는 기존 `uncertain` 보류 상태를 유지하고 `delivery_outcome`으로 `not_sent`와 `unknown`을 구분합니다. 단계·고정 오류 코드·HTTP 상태·진단 시각만 추가 기록하며 본문·인증값·원시 오류는 기록하지 않습니다. 기존 불명확 기록의 분류는 추측해 바꾸지 않습니다. Slack 성공 ID는 대기 안내 삭제 전에 저장하므로 후처리 실패나 그 도중 재시작 때문에 답변을 재전송하지 않습니다. 수신 응답과 로컬 저장 사이의 중단은 여전히 불명확으로 보존합니다.

## 큰 완료 기록의 조회

Aside 기록은 공식 REPL 안에서 완료 이벤트·모델·최종 답변 서명·소유권 확인 입력·검증 가능한 검색 출처 필드만 추려 반환합니다. 추론 내용·도구 인수·도구 결과 본문은 CLI로 가져오지 않습니다. 기존 1MiB 출력 상한을 유지하며, 그래도 초과하면 `cli_output_limit`으로 즉시 보고하고 통신 재시도 대상으로 취급하지 않습니다. 완료를 확인하지 못한 실행은 안전상 불명확 상태를 유지하므로 운영자 확인이 필요합니다.

`AsideBackend.readCompletedTurn`은 복구용 읽기 검증입니다. 등록된 세션 소유권, idle 상태, 가장 최근 턴 ID와 시작 시각, 원래 제출 입력, 완료·최종 답변·모델을 검증하며 질문을 재실행하거나 메시지를 보내지 않습니다. 실제 상태 복구와 답변 발송에는 별도 승인·DB 백업·중복 전송 확인이 필요합니다.

### Aside 프로필 창과 프리셋 조회

봇은 `u0` 계정의 열린 Aside 브라우저 창에서 프리셋을 읽습니다. 로그인 상태나 세션 목록 조회 성공만으로는 프리셋 조회 가능 여부를 확인할 수 없습니다. 시작 시 두 봇 모두 기본 프리셋을 실제로 읽고 검증하며, 실패하면 연결 준비 상태로 진입하지 않습니다.

프로필 창이 닫혔다는 안내가 나오면 Aside에서 봇이 사용하는 `u0` 프로필 창을 열고 다시 시도하십시오. 다른 계정으로 전환하거나 프로필 디렉터리를 추정해서 열지 마십시오. 새 Slack 질문의 프리셋 조회가 실패한 경우 질문은 접수·실행되지 않으며 자동 재전송하지 않습니다. 이미 제출된 작업의 불확실성 처리와 재전송 제한은 유지됩니다.

### 원격 완료 후 출력 오류

검색 출처 제목은 표시 시 최대 180자로 줄이며 URL의 HTTP(S), 자격증명 부재 및 실제 도구 출처 검증은 유지합니다. 검증된 완료 턴의 출처 오류는 `completed_output_invalid_sources`, 반환된 답변의 포맷 오류는 `completed_output_output_format_failed`로 개별 요청을 실패 처리합니다. 이 경우 모델 실행을 다시 시도하지 않으며 플랫폼 전체를 잠그지 않습니다. 완료·서명·모델·소유권 검증이 불확실한 실행은 기존 플랫폼 보류를 유지합니다. 고정 원인 코드만 저장하며 원문 오류나 인증값은 기록하지 않습니다.

기존 `execution_unknown` 요청은 패치나 재시작으로 자동 정정하지 않습니다. 운영자가 원문 소스·소유권·정확한 완료 턴·기존 전송 여부를 확인하고 파일 및 DB를 백업한 뒤 해당 요청만 복구해야 합니다. 복구 답변은 정상 outbox를 통해 한 번 전송하며 전송이 불명확하면 재전송하지 않습니다.
